# 技術限制與未來規劃

本文件記錄目前實作在**開發／競賽環境下的已知限制**，以及正式上線時的對應規劃。
這些限制多數來自「雲端服務的預設安全策略」或「為控制專案複雜度所做的取捨」，
而非架構設計缺陷；絕大多數在上線時**不需要修改程式碼**即可解除。

---

## 一、Email 通知：Amazon SES 沙箱模式

### 現況

每日摘要的 email 通知使用 Amazon SES 寄送。AWS 所有新帳號的 SES 預設處於
**沙箱模式（Sandbox）**，這是 AWS 為防止服務被用於發送垃圾郵件所設的預設保護。

沙箱模式的三項限制（本專案實測數值，region: us-west-2）：

| 項目 | 沙箱限制 |
|------|---------|
| 收件對象 | **僅能寄送至事先驗證過的 email 地址** |
| 每日寄送量 | 200 封 |
| 寄送速率 | 每秒 1 封 |

其中第一項對開發影響最大：每一位要收信的使用者，其 email 都必須先在
SES Console 完成驗證（收驗證信 → 點確認連結）。這在開發與 demo 階段
是可接受的，但顯然不適用於真實使用者自行註冊的情境。

### 上線規劃

向 AWS 申請 **Production Access**（SES Console → Account dashboard →
Request production access），審核通過後限制解除：

| 項目 | 正式模式 |
|------|---------|
| 收件對象 | **任意地址，無需事先驗證** |
| 每日寄送量 | 一般由 50,000 封起，可再申請調高 |
| 寄送速率 | 一般由每秒 14 封起 |

申請時需說明郵件用途、收件人來源、以及退訂與退信（bounce／complaint）的
處理方式。本專案的郵件屬於使用者主動設定的交易型通知（transactional），
並非行銷郵件，符合 SES 的使用政策。

**寄件地址的驗證是永久要求**，正式模式也不會取消——這是證明寄件方對該
網域／地址具有控制權的機制。上線時建議改為**驗證整個網域**而非單一地址，
並啟用 DKIM 簽章以提升送達率、降低被判為垃圾信的機率。

### 對程式碼的影響

**無。** 沙箱與正式模式的差異僅在 AWS 帳號狀態，`ses.send_email()` 的
呼叫方式完全相同。切換時只需更新 `.env` 的 `SES_SENDER_EMAIL`。

## 二、定時排程：Flask 背景執行緒

### 現況

「自動推播每日摘要」由 Flask 進程內的一條 daemon thread 實作
（`backend/services/scheduler.py`），每 60 秒檢查是否有到期的排程。

限制：**後端伺服器必須保持運行**，關閉後排程即停止。

已在實作中緩解的部分：判斷條件為「已過設定時間**且**當天尚未產生摘要」，
而非「現在剛好是設定時間」。因此伺服器若在設定時間點未啟動，之後啟動時
會自動補產生當天摘要，不會整天遺漏；同時天然具備去重效果，重複觸發
不會產生兩份摘要。

### 上線規劃

改為 **Amazon EventBridge Scheduler + AWS Lambda**，這是 AWS 處理定時
任務的標準做法：

```
EventBridge（每 5～15 分鐘觸發一次）
        ↓
      Lambda
        ↓
  讀取 Follows / Facts（DynamoDB）
        ↓
  呼叫 Bedrock 產生摘要
        ↓
  寫入 DailySummaries + 透過 SES 寄送通知
```

此架構下摘要產生完全不依賴應用伺服器的運行狀態。由於資料層
（DynamoDB）與模型層（Bedrock）本身都是雲端服務，Lambda 可直接存取，
不需要經過後端 API。

設計要點：採用**單一排程**（每 N 分鐘觸發，由 Lambda 自行掃描到期項目），
而非為每位使用者各建一條 EventBridge schedule。後者會使後端需要具備
`scheduler:CreateSchedule` 權限，並產生排程與資料庫狀態不同步的風險。

未在競賽期間採用的原因：需要額外的部署流程（打包、IAM 角色、schedule
設定），且每次調整 prompt 都需重新部署，不利於開發期的快速迭代。

## 三、Email 通知的觸發條件

### 現況

Email 僅在**摘要由排程新產生時**寄送。若當天已有人手動點擊「產生每日
摘要」，排程會判定當天摘要已存在而跳過，因此不會寄信。

這是刻意的取捨：以「當天是否已有摘要」作為去重依據，即可保證不重複寄送，
而無需在資料庫額外維護「已寄送」狀態欄位。

### 上線規劃

若需要「無論摘要由何種方式產生都寄送通知」，可在 `DailySummaries` 增加
`notified_at` 欄位作為寄送狀態記錄，將寄信判斷與產生流程解耦。

另可考慮讓使用者分別控制「站內通知」與「Email 通知」（目前設定推播時間後
兩者同時啟用），實作上為 `Follows` 增加一個布林欄位。

## 四、資料查詢：DynamoDB Scan 與分頁

### 現況

本專案的資料存取採用 `scan` + `FilterExpression`，並以 `account_id`
作為使用者資料隔離的依據。這在資料量小的情境下運作正常且實作簡潔。

需注意的技術特性：DynamoDB 的 `scan` 單次呼叫最多讀取 1MB 資料，且
**`FilterExpression` 是在讀取之後才套用**。因此當資料量成長時，若未處理
分頁（`LastEvaluatedKey`），可能出現「該筆資料存在但查詢結果為空」的情況。

背景排程的查詢已實作分頁迴圈，因為背景任務的資料遺漏不會被使用者察覺。

### 上線規劃

改用 `query` 搭配既有的 Global Secondary Index（`Facts` 表已建立
`account_id-index`），並補齊分頁處理。相較 `scan` 可同時改善正確性
與查詢成本——`query` 僅讀取符合分區索引鍵的項目，不需掃描全表。

## 五、知識庫檢索方式

### 現況

衛教知識庫（`HealthKnowledgeBase`）採用**關鍵字子字串比對**檢索：
每筆知識條目定義 `keywords`，對話時比對使用者訊息，命中則將該條目內容
注入 AI 的參考上下文。

優點是行為完全可預測、可追溯——命中哪一條、為什麼命中，都能從
`keywords` 直接對照，這對醫療衛教情境的可解釋性有實質意義。

限制是無法處理語意相近但用詞不同的表達。知識庫資料已預留
`keywords_spoken` 欄位收錄長者的口語說法（如「記性變差」、「忘東忘西」）
以緩解此問題。

### 上線規劃

導入 Amazon Bedrock Knowledge Bases 或 OpenSearch 的向量檢索，
以語意相似度取代字面比對。建議採**混合檢索**：關鍵字比對命中者優先
（保留可解釋性），向量檢索作為補充，避免完全失去「為什麼引用這條」的
追溯能力。

## 六、憑證管理

### 現況

開發環境使用 AWS Academy／Workshop 提供的臨時憑證
（`ASIA` 開頭的 STS credentials），存放於 `backend/.env`。
此類憑證數小時後即失效，需重新取得。

程式已針對此情況處理：偵測到 `ExpiredToken`、`InvalidClientTokenId`、
`UnrecognizedClientException` 等錯誤碼時，會輸出明確的中文提示指引更新
憑證，而非拋出難以判讀的堆疊追蹤。

### 上線規劃

- 部署於 EC2／ECS／Lambda 時改用 **IAM Role**，由執行環境自動取得
  短期憑證並輪替，程式端完全不接觸金鑰
- 敏感設定改存 **AWS Secrets Manager** 或 **Systems Manager Parameter Store**
- 依最小權限原則收斂 IAM 政策至實際使用的動作
  （目前需要：DynamoDB 讀寫、`bedrock:InvokeModel`、`polly:SynthesizeSpeech`、
  `transcribe`、`ses:SendEmail`、`cognito-idp:ListUsers`）

## 七、網路層可靠性

### 現況

開發環境曾出現間歇性的 HTTPS 連線重置（Windows Error 10054），
影響 Cognito token 交換與 JWKS 公鑰取得，導致登入隨機失敗。

已實作對應處理：`backend/services/http.py` 提供帶自動重試的
HTTP session（連線層級最多重試 5 次，採指數退避 0.5s → 1s → 2s → 4s，
並設定連線 5 秒／讀取 15 秒的逾時），供對外呼叫使用。

### 上線規劃

將相同的重試策略套用至所有對外呼叫；並為 Bedrock、Polly、Transcribe
等呼叫加入 botocore 層級的重試設定與斷路器（circuit breaker），
避免單一服務異常時造成請求堆積。

## 八、限制總覽

| 項目 | 開發／競賽環境 | 正式環境規劃 | 需改程式碼 |
|------|--------------|-------------|-----------|
| Email 收件人 | 須事先在 SES 驗證 | 申請 Production Access 後無限制 | 否 |
| Email 寄送量 | 200 封／日 | 50,000 封／日起 | 否 |
| 定時排程 | Flask 背景執行緒，伺服器需開啟 | EventBridge + Lambda | 是 |
| Email 觸發 | 僅排程產生時寄送 | 增加 `notified_at` 狀態欄位 | 是 |
| 資料查詢 | `scan` + Filter | `query` + GSI + 分頁 | 是 |
| 知識庫檢索 | 關鍵字比對 | 關鍵字 + 向量混合檢索 | 是 |
| 憑證 | `.env` 存放臨時憑證 | IAM Role + Secrets Manager | 否 |

## 九、小結

上述限制可分為兩類。

**第一類是雲端服務的預設保護機制**，例如 SES 沙箱模式。這類限制不反映
系統設計品質，解除方式是提交申請，且不需要修改任何程式碼。

**第二類是為控制專案複雜度所做的主動取捨**，例如以 Flask 背景執行緒
代替 EventBridge + Lambda、以關鍵字比對代替向量檢索。這類選擇讓功能能在
有限時間內完整實作並驗證，同時在架構上保留了後續替換的空間——例如摘要
產生邏輯已抽離為獨立的服務層函式（`services/daily_summary.py`），
不依賴 Flask 的請求上下文，可直接移植至 Lambda 而無需重寫。
