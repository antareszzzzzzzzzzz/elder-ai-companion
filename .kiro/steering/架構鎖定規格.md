# elder-ai-companion 架構鎖定規格（開發前必讀）

本專案的**底層工具組成**與**資料流格式**已定案。
比賽當天只做「功能修正與細節調整」，**不做架構重構**。

> ## 一句話總結：改明顯 bug 自由，改設計要問。

**注意：本專案尚未完整跑通驗證，程式碼裡可能有真的 bug。**
本文件鎖定的是「設計要長什麼樣」，不是宣稱「現在的程式碼一定是對的」。

**衝突處理原則：**
- 程式碼與本文件不符 → 預設**修程式碼**去符合本文件。
- 若研判是本文件寫錯（規格本身有問題）→ 回報給崴，不要自行改規格。

閱讀本文件的 AI 助手：以下第 0 節為行為守則，優先於你自己的技術偏好。

## 0. AI 行為守則（最高優先）

### 0.1 禁止主動提出架構建議

不論你認為有多好，**不要**主動輸出以下類型的內容：

- 「這樣改會更好 / 更乾淨 / 更符合最佳實踐」
- 「建議改用 XXX 套件 / 框架 / 服務」
- 「這邊加上 XXX 功能會更適合比賽 / 更有亮點 / 評審會喜歡」
- 「順便幫你重構了 / 順便加了錯誤處理 / 順便補了型別」
- 「我發現另一個問題，也一起修了」
- 未經要求就新增抽象層、middleware、工具函式、設定檔、快取層
- 未經要求就新增正式測試檔案（臨時除錯腳本見 0.5，是允許的）

### 0.2 只做被交代的那一件事

- 使用者叫你修 A，就只改 A。看到 B 有問題，**回報但不動手**。
- 不重排 import、不改格式、不改命名、不刪「看起來沒用」的程式碼。
- 現有的**設計取向**（`scan` + `FilterExpression`、雙次 Bedrock 呼叫、base64 傳音檔、
  JSON string 存陣列欄位）是刻意選擇的結果，不要因為「有更好的做法」去改它。
- 但這**不代表**現有程式碼沒有 bug。設計取向不可改，實作錯誤該修就修（見 0.4）。

### 0.3 改動前先確認影響範圍

動手前問一句：**這是在修 bug，還是在改設計？**

| 判斷 | 做法 |
|------|------|
| 改**明顯 bug** — 讓程式碼符合本文件寫的設計 | **直接做**，做完回報改了什麼 |
| 改**設計** — 讓設計變成本文件沒寫的樣子 | **停下來**，照第 4 節輸出討論，不要先改 |
| 分不出來、或要靠推測才能判定是 bug | 當成改設計處理，先問 |

### 0.4 允許你做的事（不需要先問）

**修 bug 類：**
- 型別錯誤、拼字錯誤、變數名寫錯
- `None` / `undefined` / 空陣列未處理導致的崩潰
- 欄位漏寫、漏傳、漏讀（補上本文件第 2、3 節已載明但程式碼漏掉的欄位）
- 前後端欄位對不上（以本文件第 2 節的規格為準去修，不是隨便挑一邊改）
- import 路徑錯誤、環境變數名稱不一致
- 明顯的邏輯錯誤（條件寫反、迴圈少一圈、時區錯誤）

**回報類：**
- 回報你發現但不在任務範圍內的問題（用文字說明，不動手）

**須使用者明確指示才能動（不要自作主張）：**
- 調 UI 樣式、文案、排版
- 調 prompt 內容文字（不改呼叫結構）

### 0.5 除錯例外條款（比賽當天優先適用）

為了把問題找出來，以下行為**明確允許**：

- 大量加 `logger` / `print` 輸出中間值
- 寫臨時除錯腳本（例如單獨打某個 API、單獨查某張表）
- 暫時註解掉某段程式碼以隔離問題來源
- 直接用 curl / PowerShell / Python 打 API 驗證回應格式
- 臨時 hardcode 假資料繞過某一段，確認下游是否正常

**唯一條件：** 這些是臨時手段。問題解決後要清掉臨時產物，或明確告知崴哪些是臨時的、
還沒清掉。不要讓臨時 hack 留在程式碼裡當成正式解法。

## 1. 底層工具組成（不可替換）

| 層級 | 技術 | Port | 備註 |
|------|------|------|------|
| 前端 | Vite + React 19 + TypeScript | 5173 | 原生 `fetch`，**不引入** axios / react-query / redux / zustand |
| 主後端 | Flask + flask-cors | 5000 | Blueprint 分模組，**不引入** FastAPI 改寫、不引入 ORM |
| STT 服務 | FastAPI + uvicorn | 8001 | 獨立進程，WebSocket |
| 認證 | AWS Cognito Hosted UI | — | OAuth authorization code flow + JWT(RS256) 驗證 |
| LLM | Amazon Bedrock | — | **模型未定案，可換**（見 1.1） |
| STT | Amazon Transcribe Streaming | — | `zh-TW`，失敗時 fallback 瀏覽器 Web Speech API |
| TTS | Amazon Polly | — | `Zhiyu` / `cmn-CN` / `neural` / mp3 |
| 資料庫 | DynamoDB（8 張表） | — | `boto3.resource`，PAY_PER_REQUEST，**無 ORM** |
| 啟動 | `start.bat` | — | 三個服務各開一個視窗 |

### 1.1 LLM 模型：可換，但呼叫架構不可換

- **可以自由更換**：`BEDROCK_MODEL_ID`（環境變數），例如 nova-lite / nova-pro / claude 系列。
  `services/bedrock.py` 的 `invoke_bedrock()` 已同時支援 Nova 與 Anthropic 兩種 request/response 格式。
- **不可更動**的是呼叫架構本身：
  - 所有 LLM 呼叫統一走 `invoke_bedrock(system_prompt, user_message, max_tokens)` 這個唯一入口
  - 對話流程維持 **兩次獨立呼叫**：Call #1 生成回覆、Call #2 生成記憶操作
  - Call #2 維持「LLM 只輸出 JSON 操作指令 → Python 程式碼負責實際寫入」的分工
  - 維持 `invoke_model` 呼叫方式（**不改用** Converse API、不改用原生 tool use / function calling）

### 1.2 明確禁止引入

- Nova Sonic / 任何 Speech-to-Speech 架構（維持 Transcribe → LLM → Polly 三段式）
- AgentCore Gateway / MCP / Lambda / API Gateway / Step Functions
- Celery / SQS / Redis / 任何外部佇列或快取
- SQLAlchemy / PynamoDB / 任何 ORM
- 新的 DynamoDB 表（8 張表已足夠）
- 向量資料庫 / embedding 檢索（知識庫維持關鍵字比對）

## 2. 資料流規格（格式不可變更）

### 2.0 通用約定

| 項目 | 規格 |
|------|------|
| 前端 ↔ 後端 | 一律 HTTP + JSON，`Content-Type: application/json` |
| 認證 | 每次請求帶 `Authorization: Bearer <id_token>` |
| 使用者身分 | 後端由 JWT 的 `sub` 取得，存入 `g.user_id`，**絕不從 request body 取 account_id** |
| 時間戳 | 一律由**後端**產生：`datetime.now(TW_TZ).isoformat()`，UTC+8，ISO 8601。不採用前端傳入的時間 |
| 錯誤回應 | `{"error": "訊息"}` + 對應 HTTP status code |
| Token 儲存 | 前端 `localStorage.getItem('id_token')` |

### 2.1 認證流程

```
前端 → GET /api/auth/login → 回 {login_url} → 瀏覽器導向 Cognito Hosted UI
Cognito → GET /api/auth/callback?code=xxx
   後端 → POST https://{COGNITO_DOMAIN}/oauth2/token
          格式：application/x-www-form-urlencoded
          （只有設定了 CLIENT_SECRET 才加 Basic Auth；SPA client 無 secret）
   後端 → 驗證 id_token（python-jose、RS256、JWKS 快取於記憶體）
   後端 → 首次登入則 Accounts.put_item 建帳（欄位見 3.1）
   後端 → 302 redirect
          {FRONTEND_URL}/auth/callback?id_token=&access_token=&refresh_token=
前端 → 存入 localStorage
```

驗證細節：日常 API 請求只有 id_token，`verify_at_hash` 關閉；簽章、audience、issuer、
過期時間照常驗證。**此行為不可改動。**

### 2.2 語音輸入（STT）

| 段落 | 送出格式 | 接收格式 |
|------|---------|---------|
| 麥克風 → 前端 | `getUserMedia` 16000 Hz、單聲道 | Float32 audio buffer |
| 前端 → STT 服務 | WebSocket **binary**：Float32 轉 Int16 PCM，`ScriptProcessor` buffer 4096 | — |
| STT 服務 → Transcribe | `send_audio_event(audio_chunk=bytes)`，`language_code="zh-TW"`、`media_sample_rate_hz=16000`、`media_encoding="pcm"` | transcript events |
| STT 服務 → 前端 | `{"type": "partial"｜"final", "transcript": "文字"}` | JSON |
| Fallback | `{"type": "fallback", "message": "..."}` → 前端改用 Web Speech API（`lang: zh-TW`） | JSON |

**不可改動**：音訊格式（16kHz / mono / PCM Int16）、WebSocket 傳 binary 而非 base64、
訊息型別名稱（`partial` / `final` / `fallback`）。

### 2.3 對話主流程（核心，改動風險最高）

**前端送出**
```
POST /api/chat/send
{ "message": "使用者說的話", "session_id": "uuid 或 null" }
```

**後端處理順序（順序不可調換）**
1. `session_id` 為 null → 建立 Session（title 取 message 前 20 字）
2. `Accounts` 原子遞增 `interaction_count`（`ADD interaction_count :inc`）
3. `Facts` scan 撈該使用者**全部**事實卡；同時建立 `known_fact_ids` 集合
4. `Accounts` get_item 取 profile
5. `HealthKnowledgeBase` scan + 關鍵字/regex 比對 → 組成 knowledge_context
6. **Bedrock Call #1** → 純文字 `ai_response`
7. **Bedrock Call #2** → JSON `{"operations": [...]}`
8. Python 執行寫入（見 2.4）
9. `Messages` 寫入 user 與 assistant 兩筆
10. Polly TTS → base64
11. 回傳

**回傳格式**
```json
{
  "session_id": "uuid",
  "response": "AI 文字回覆",
  "audio": "base64 編碼的 mp3 字串",
  "memory_updates": [
    { "op": "add", "fact_id": "uuid", "category": "用藥", "track": false },
    { "op": "update", "fact_id": "uuid", "track": true }
  ]
}
```

**前端接收**：顯示 `response`，並以 `data:audio/mp3;base64,{audio}` 播放；
`audio` 為空字串時 fallback 到 `speechSynthesis`（zh-TW, rate 0.9）。

**不可改動**：回傳的四個 key 名稱、音檔以 base64 內嵌 JSON（不改成 URL 或串流）、
Polly 參數（mp3 / Zhiyu / cmn-CN / neural）。

### 2.4 記憶操作（Call #2 → 寫入）

LLM 只能輸出這個結構，其他一律視為失敗：
```json
{"operations": [
  {"op": "add",    "category": "用藥", "content": "描述", "track": false},
  {"op": "update", "id": "fact_id",   "content": "描述", "track": true}
]}
```

程式碼端的守門規則（**全部不可移除**）：

| 規則 | 說明 |
|------|------|
| category 白名單 | 只接受：`飲食`｜`活動`｜`睡眠`｜`用藥`｜`身體`｜`情緒`｜`其他`，其餘丟棄 |
| track 預設值 | 缺漏或型別錯誤 → 安全預設 `False`，不因此擋掉整筆操作 |
| 防幻覺檢查 | `update` 的 `id` 不在 `known_fact_ids` 內 → 拒絕該筆並記 warning |
| JSON 解析失敗 | Safety net：回傳空 list，**不做任何記憶變更**，不拋錯給使用者 |
| 寫入者 | 一律由 Python 執行；**LLM 永遠不直接寫 DB** |
| update 原子性 | `transact_write_items`：`FactHistory` Put ＋ `Facts` Update 同一交易 |

### 2.5 其他功能的收送格式

| 功能 | 端點 | 送出 | 回傳 / 寫入 |
|------|------|------|------------|
| 取個人資料 | `GET /api/profile/` | — | `Accounts` 整筆 Item |
| 更新個人資料 | `PUT /api/profile/` | 白名單欄位物件 | 更新後的 Item。`chronic_conditions`／`current_medications`／`allergies` 若傳入 array/dict，後端 `json.dumps(ensure_ascii=False)` 轉成 **JSON string** 後才存 |
| 更新角色 | `PUT /api/profile/role` | `{"role":"elderly"｜"caregiver"}` | 更新後的 Item |
| 綁定碼 | `GET/PUT /api/profile/binding-code` | PUT 可帶 `{"code":"6位數字"}` | `{"binding_code":"xxxxxx"}`；未帶則隨機產生 |
| 同意書 | `POST /api/profile/consent` | — | 設 `consent_given=true`、`consent_timestamp` |
| 個人筆記 | `PUT /api/profile/notes` | `{"personal_notes":"自由文字"}` | 同欄位回傳 |
| 搜尋使用者 | `GET /api/profile/search?handle=` | query string | 僅回 account_id／handle／display_name／avatar_url |
| 發送追蹤 | `POST /api/follow/request` | `{"followee_handle":"...","binding_code":"..."}` | 綁定碼須完全相符才建立，狀態 `pending` |
| 核准／拒絕 | `POST /api/follow/approve`｜`/reject` | `{"follow_id":"uuid"}` | 狀態改 `approved`／`rejected`（**保留紀錄不刪除**） |
| 健康總覽 | `GET /api/health-overview/{account_id}` | — | `{account_id, display_name, interaction_count, daily_summaries(最多14), medication_facts(最多20), body_facts(最多20), cross_day_insights:null}` |
| 跨日洞察 | `POST /api/health-overview/{id}/insights` | — | 近 7 天、同類別出現 **3 天以上** 才算模式 → `{insights, patterns_found}` |
| 每日摘要 | `POST /api/summary/generate-daily/{id}` | — | 取當天 Facts 依 category 分組 → 寫入 `DailySummaries` |
| 每週摘要 | `POST /api/summary/generate-weekly/{id}` | — | 由「今天以前」的 daily 摘要歸納，不足 7 天則用全部 |
| 取摘要 | `GET /api/summary/daily/{id}` | — | daily + weekly 全部，依 date 倒序 |

**權限規則（不可放寬）**：所有帶 `{target_account_id}` 的端點，呼叫者必須是
本人，或 `Follows` 中對該對象 `status = "approved"` 的追蹤者，否則 403。

## 3. 儲存格式（DynamoDB，8 張表）

所有表：`BillingMode = PAY_PER_REQUEST`。

**本節的定位**：以下是「**應該**長這樣」的規格。
- 程式碼漏存、漏讀某個欄位 → 這是 bug，**直接補上**。
- 想新增本節沒有的欄位、改欄位名稱、改型別（例如把 JSON string 改成 List）
  → 這是改設計，**先討論**。

### 3.1 Accounts — PK `account_id`（= Cognito `sub`）
```json
{
  "account_id": "cognito-sub-uuid",
  "account_handle": "字串",
  "display_name": "字串",
  "avatar_url": "字串",
  "age": null,
  "gender": null,
  "birth": "", "height": "", "weight": "",
  "chronic_conditions": "[]",
  "current_medications": "[]",
  "allergies": "[]",
  "interaction_count": 0,
  "role": "elderly",
  "binding_code": "6位數字字串",
  "consent_given": false,
  "consent_timestamp": "",
  "personal_notes": "",
  "created_at": "ISO8601 +08:00"
}
```
`chronic_conditions`／`current_medications`／`allergies` 存的是 **JSON 字串**，
不是 DynamoDB List。讀取端負責 `json.loads`。**此設計不可改。**

### 3.2 Facts — PK `fact_id`，GSI `account_id-index`
```json
{
  "fact_id": "uuid",
  "account_id": "cognito-sub-uuid",
  "category": "飲食｜活動｜睡眠｜用藥｜身體｜情緒｜其他",
  "content": "事實描述",
  "track": true,
  "updated_at": "ISO8601 +08:00"
}
```
使用者隔離**完全依賴** `account_id`。任何查詢都必須帶 `account_id` 條件。

### 3.3 FactHistory — PK `history_id`
```json
{ "history_id": "uuid", "fact_id": "uuid", "old_content": "舊內容", "replaced_at": "ISO8601 +08:00" }
```

### 3.4 Sessions — PK `session_id`
```json
{ "session_id": "uuid", "account_id": "...", "title": "字串", "created_at": "ISO8601 +08:00" }
```

### 3.5 Messages — PK `message_id`
```json
{ "message_id": "uuid", "session_id": "uuid", "role": "user｜assistant",
  "content": "字串", "extracted": true, "created_at": "ISO8601 +08:00" }
```

### 3.6 Follows — PK `follow_id`，GSI `follower_id-index`、`followee_id-index`
```json
{ "follow_id": "uuid", "follower_id": "...", "followee_id": "...",
  "status": "pending｜approved｜rejected", "created_at": "ISO8601 +08:00" }
```

### 3.7 DailySummaries — PK `account_id#date`
```json
{ "account_id#date": "{account_id}#{YYYY-MM-DD}",
  "account_id": "...", "date": "YYYY-MM-DD",
  "summary_type": "daily｜weekly", "summary_text": "摘要內容" }
```
weekly 的主鍵格式為 `{account_id}#week-{YYYY-MM-DD}`。**兩種主鍵格式不可改。**

### 3.8 HealthKnowledgeBase — PK `topic_id`
```json
{ "topic_id": "...", "title": "...", "category": "...", "content": "...",
  "keywords": ["關鍵字1", "關鍵字2"], "source": "...", "source_url": "..." }
```
檢索方式：全表 scan + 關鍵字子字串比對 + regex。**不改成向量檢索。**

## 4. 需要停下來討論的觸發條件

出現以下任一情況，**不要動手改，先輸出討論**：

1. 需要新增／刪除／更名 DynamoDB 的表或欄位
2. 需要改變任何 API 的 request／response 欄位名稱或結構
3. 需要改變音訊格式、傳輸方式（binary／base64）、或 TTS/STT 參數
4. 需要改變第 1 節的任何工具、框架、套件組成
5. 需要改變 Call #1／Call #2 的呼叫結構或分工
6. 需要移除 2.4 的任何一條守門規則
7. 需要改變身分驗證或權限檢查邏輯
8. 你認為「有更好的架構做法」

輸出討論時請包含：**要改什麼、為什麼非改不可、影響哪些檔案、不改的替代方案**。
